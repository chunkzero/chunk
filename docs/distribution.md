# SDK distribution

How the chunk SDK is packaged, installed and published. A release of the SDK has two parts that share one version:

- **The CLI archive**, `chunk-<version>-linux-x64.tar.gz` with a `.sha256` checksum, attached to a GitHub release. It
  holds the `chunk` executable, the native TypeScript compiler it type-checks projects with (under `toolchain/`), and
  the license. The CLI embeds the TypeScript SDK, the project templates, the Gradle wrapper and the version pins that
  `chunk create` writes.
- **The JVM artifacts**, published to `https://maven.chunkzero.com` under `dev.chunkzero`: `proto`, `backend-api`,
  `backend-client`, `backend-client-kotlin`, `runtime`, `runtime-minestom`, `runtime-minestom-kotlin`, the Gradle plugin
  and its three plugin markers. Each library has `-sources.jar` and `-javadoc.jar` (Dokka HTML) artifacts. Projects
  resolve these through Gradle; the CLI archive contains no JARs.

The archive targets Linux x64 with glibc and OpenSSL 3, tested on Ubuntu 24.04. Users need Java to run Gradle; the
Minestom runtime needs Java 25, which the generated projects download through Gradle's toolchain resolver. Building a
project needs no Rust, Node, pnpm or chunk checkout. Minestom itself is the `net.minestom:minestom:master-SNAPSHOT`
build of [chunkzero/minestom-me](https://github.com/chunkzero/minestom-me), served from
`https://maven.chunkzero.com/snapshots`.

## Versions

The Cargo workspace version is the SDK version, and the `chunk` version in `gradle/libs.versions.toml` must equal it:
packaging refuses to run otherwise, and the CLI refuses to create projects from a catalog of another version. Change
both together. A project keeps the versions it was created with in `settings.gradle.kts`.

The Gradle wrapper files in the repository root are generated by Gradle and embedded in the CLI. To update Gradle,
regenerate them with the `wrapper` task and rebuild the CLI.

## Install

```sh
curl --fail --location https://github.com/chunkzero/chunk/releases/download/v0.1.0/install.sh -o install.sh
sh install.sh 0.1.0
export PATH="$HOME/.local/bin:$PATH"
chunk --version
```

`install.sh VERSION [ARCHIVE]` downloads the archive and its checksum from the GitHub release (or copies a local
`ARCHIVE` and the `ARCHIVE.sha256` beside it), verifies both the checksum and the CLI's version, installs it to
`~/.local/share/chunk/VERSION` and links `~/.local/bin/chunk` to it. `CHUNK_INSTALL_DIR` replaces the `~/.local` prefix.
It refuses to overwrite an installed version, or a `bin/chunk` that is not a symlink. Keep the installed directory
intact: the CLI finds its TypeScript compiler next to its executable.

## Build and verify locally

```sh
just package-cli
python3 scripts/check-sdk.py target/dist/chunk-0.1.0-linux-x64.tar.gz target/dist/maven
```

`just package-cli` builds the release CLI and runs `scripts/package-sdk.py`, which writes the archive, its checksum and
a `maven/` repository with every JVM artifact to `target/dist/`. It refuses to replace existing outputs; pass
`--output DIRECTORY` for another candidate of the same version, or `--chunk PATH` to package another CLI build.

`scripts/check-sdk.py` checks the sources and documentation JARs, installs the archive into a temporary prefix, serves
the Maven directory over local HTTP, and creates, generates and builds a Java and a Kotlin project against them,
checking the resulting releases. Those projects neither include the chunk build nor read this checkout.

To try unpublished artifacts in your own project, set its `chunk.mavenRepository` Gradle property to
`file:///absolute/path/to/target/dist/maven`.

## Nightly builds

The `Nightly CLI` workflow ([`.github/workflows/nightly.yml`](../.github/workflows/nightly.yml)) builds the CLI archive
for Linux, macOS (x64 and arm64) and Windows x64 every day `main` has changed, and on manual runs from `main`. Each
archive is `chunk-<version>-<os>-<arch>.tar.gz` with a `.sha256`, where the version is
`<workspace version>-nightly.<UTC date>.g<12-character commit>`, and the CLI reports that version. They are published as
a GitHub prerelease `v<version>`; the 30 newest are kept. Nightlies carry no JVM artifacts, so `chunk create` still pins
the workspace version's. Install them through the [Chunkzero aqua registry](https://github.com/chunkzero/aqua-registry)
as `chunkzero/chunk-nightly`.

`scripts/package-sdk.py --no-maven` packages the archive for the host platform, and `scripts/nightly.py` plans the
version and publishes the verified archives. Pull requests that change them run the packaging once they are ready for
review.

## Publishing

The `SDK distribution` workflow ([`.github/workflows/sdk.yml`](../.github/workflows/sdk.yml)) packages the SDK on a
build runner and verifies it in a clean Ubuntu 24.04 container that has only Java and the verification scripts. It runs
on pull requests that change distribution inputs once they are ready for review, and on manual runs. The handoff
artifact is deleted when the run ends.

### One-time setup

1. The Maven repository is a [Maven R2](https://github.com/chunkzero/maven-r2) deployment at
   `https://maven.chunkzero.com`, whose `default/releases` repository is public and served from the origin root.
2. In its console, create a publishing token restricted to `default/releases`, the `dev/chunkzero/` prefix and the
   publishing operations.
3. Create the GitHub environment `sdk-release`, restricted to `main` with a required reviewer, and add the token as the
   environment secret `MAVEN_R2_TOKEN`.

The workflow installs Maven R2 CLI `v0.1.0`; keep it compatible with the deployed service (see the
[Maven R2 publishing guide](https://github.com/chunkzero/maven-r2#publishing)).

### Publish a version

Merge the version change, then run `SDK distribution` from `main` with `publish` enabled. After packaging and
verification pass, the workflow:

1. creates or reuses a draft GitHub release `v<version>` on that commit and uploads the archive, checksum and
   `install.sh`;
2. stages the verified Maven files through the Maven R2 CLI with `scripts/publish-maven.py`, which the CLI commits only
   after every upload succeeds;
3. checks that the public Maven endpoint serves the published POM; and
4. publishes the GitHub release, as a prerelease for versions with a `-` suffix.

Publication uses the exact files that passed verification. Maven R2 makes a publication visible all at once and keeps
releases immutable: re-publishing identical files succeeds, while different files at an existing version fail, so never
reuse a version for different artifacts. A failed publication leaves the GitHub release as a draft. The run's artifact
is gone once it ends, so retry by running the workflow again. If the final Maven commit fails transiently, the CLI
leaves the session open and prints its ID; `maven-r2 session status`, `commit` or `abort` with that ID, the same server
and publishing credentials inspects, finishes or discards it within 24 hours.
